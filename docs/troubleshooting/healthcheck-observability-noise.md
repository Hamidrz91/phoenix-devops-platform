# Docker Healthcheck Created Observability Noise

## Problem

After adding a Docker healthcheck to the Phoenix application, the container correctly reported:

    healthy

The healthcheck called:

    GET /health

every 30 seconds.

However, Phoenix was also instrumented with:

    Prometheus custom request metrics
    OpenTelemetry Flask tracing

This meant that internal Docker healthcheck traffic was being treated like normal application traffic.

As a result, repeated healthcheck requests could increase request counters and create unnecessary traces in Tempo.

## Investigation

The Phoenix application already excluded the Prometheus metrics endpoint from tracing:

    FlaskInstrumentor().instrument_app(
        app,
        excluded_urls="/metrics",
    )

The custom request metrics also skipped only the metrics endpoint:

    if endpoint == "metrics":
        return response

After Docker healthchecks were enabled, Gunicorn access logs showed requests such as:

    "GET /health HTTP/1.1" 200

generated by:

    Python-urllib/3.12

These requests were internal health probes rather than real user traffic.

The application was therefore changed so that both:

    /metrics
    /health

were excluded from custom request metrics and OpenTelemetry tracing.

## Root Cause

The healthcheck endpoint was designed for infrastructure health verification, but it was not excluded from application-level observability instrumentation.

Docker periodically called:

    /health

and the application treated those requests like normal traffic.

This created artificial observability data that did not represent user activity.

## Solution

The OpenTelemetry Flask instrumentation was changed from:

    FlaskInstrumentor().instrument_app(
        app,
        excluded_urls="/metrics",
    )

to:

    FlaskInstrumentor().instrument_app(
        app,
        excluded_urls="/metrics,/health",
    )

The custom Prometheus request metrics were also changed from:

    if endpoint == "metrics":
        return response

to:

    if endpoint in {"metrics", "health"}:
        return response

This preserved the Docker healthcheck while preventing internal probe traffic from affecting custom application metrics and traces.

## Verification

A dedicated test container was started with:

    OTEL_SERVICE_NAME=phoenix-health-filter-test

Five health requests were generated:

    GET /health
    GET /health
    GET /health
    GET /health
    GET /health

One database request was also generated:

    GET /db-check

The custom Prometheus metrics were then queried.

The result included:

    phoenix_http_requests_total{endpoint="db_check",method="GET",status="200"} 1.0

There was no metric with:

    endpoint="health"

Tempo was then queried for traces from:

    phoenix-health-filter-test

Only one trace was returned:

    GET /db-check

No:

    GET /health

trace was present.

The same behavior was later verified on the deployed Phoenix service.

A time-bounded Tempo query contained:

    GET /db-check

and no healthcheck traces.

## Important Note

The healthcheck is still visible in Gunicorn access logs.

This is intentional.

The goal is not to hide the request completely.

The goal is to prevent internal health probes from affecting:

    application request counters
    request latency metrics
    distributed traces

while still retaining low-level access logs for troubleshooting.

## Lesson Learned

Infrastructure-generated traffic should be separated from real application traffic when designing observability.

Health probes can run frequently and may distort:

    request rates
    latency measurements
    tracing volume

if they are treated like normal requests.

A production observability setup should deliberately decide which internal endpoints belong in metrics and traces instead of instrumenting every request by default.
